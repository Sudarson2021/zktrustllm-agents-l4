\section{Scientific Evaluation Methodology}
The evaluation is organised as a four-stage pipeline. Stage 1 establishes the n8n workflow, response matrix, KPI plan, and formal-verification preparation. Stage 2 converts outputs into a clean 240-record dataset. Stage 3 adds direct runtime hooks. Stage 4 extends the audit micro-benchmark to Ethereum Sepolia public-testnet evidence.

\subsection{Evaluation Matrix}
The experiment covers six variants: Full L4, No-ZK, Oracle-only, RBAC-only, No-IPFS, and No-policy-gate. Each variant is evaluated over four impairment profiles and ten repetitions, giving 240 clean records.

\subsection{Multi-Model n8n Tool-Scenario Extension}
To test whether the orchestration layer remains reproducible across different AI tools, the n8n evaluation is extended with three bounded tool scenarios: evidence summarisation, claim-boundary review, and policy-ladder checking. Each scenario is executed against Claude, DeepSeek, and Mistral through the same local evidence pipeline. The measured outcomes are provider latency, JSON parse success, schema compliance, claim-boundary agreement, action-ladder violation count, output size, and token usage where returned by the provider API. This extension evaluates bounded reasoning and orchestration robustness only; it does not expand the trusted computing base or claim semantic correctness of LLM reasoning.

\subsection{KPI Classes}
The dataset distinguishes direct runtime KPIs, configured impairment-profile KPIs, public-testnet audit KPIs, reproducibility metadata, and missing values. This prevents overclaiming. Configured RTP/DTLS-RTP jitter and loss values are scenario-control parameters until replaced by packet-capture or O-RAN telemetry measurements.

\subsection{Consensus-Layer Sensitivity Protocol}
The consensus mechanism belongs to the execution network, not to the Solidity contract. We therefore add a paired public-testnet protocol that deploys identical \texttt{Stage3AnomalyLedger} bytecode to Ethereum Sepolia and IoTeX testnet. Sepolia follows the Ethereum PoS protocol but uses a permissioned validator set controlled by client and testing teams \cite{ethereumNetworks}; IoTeX documents Randomized Delegated Proof of Stake (Roll-DPoS), with delegated candidate election, VRF committee selection, and PBFT voting \cite{iotexRollDpos}. IoTeX testnet is EVM compatible and uses chain ID 4690 \cite{iotexTestnet}.

Each session executes three excluded warm-up pairs and 30 measured pairs. A matched pair carries identical commitment and evidence digests, with both transactions submitted concurrently from one client host. The publication gate requires at least three sessions, verifies chain identities and runtime-code hashes, and rejects incomplete receipts, events, block samples, or security probes. The primary metric is client-observed submission-to-first-inclusion latency; it includes RPC/client overhead and public-testnet load and is not economic finality. Median confidence intervals use a two-level hierarchical bootstrap over sessions and within-session pairs. Gas prices are recorded but not converted into a cross-asset cost comparison.

\subsection{Consensus-Protocol and SHA-2 Extension}
Consensus and evidence hashing are separate layers. Ethereum uses the Gasper
consensus mechanism, whereas IoTeX uses Roll-DPoS with PBFT-style finalisation
\cite{ethereumGasper,iotexRollDpos}. Figure~\ref{fig:consensus-protocols}
therefore keeps the existing Sepolia and IoTeX measurements distinct from
Raft, a crash-fault-tolerant leader/majority protocol
\cite{raftPaper,fabricRaft}, and QBFT, a Byzantine-fault-tolerant permissioned
EVM protocol requiring at least a two-thirds validator supermajority
\cite{besuQbft}. The latter two rows are protocol-property comparisons unless
raw deployment evidence passes the same publication gate.
The measured latency figure remains restricted to the 90 matched
Sepolia--IoTeX pairs; Raft and QBFT are not inserted as synthetic bars.

SHA-256 and SHA-512 are one-way SHA-2 hash functions, not encryption algorithms
\cite{nistFips1804}. Table~\ref{tab:sha2-semantics} and
Fig.~\ref{fig:sha2-paths} define a fair comparison: identical retained payload
bytes are hashed off chain and the complete 32-byte or 64-byte digest is
anchored through identical \texttt{HashCommitmentLedger} bytecode. This measures
digest anchoring. Solidity exposes SHA-256 through a precompile-backed built-in,
but the standard EVM has no SHA-512 precompile \cite{solidityCrypto}; the
separate on-chain SHA-256 path is therefore not misrepresented as a symmetric
SHA-256/SHA-512 computation benchmark.

The separate local primitive microbenchmark uses one isolated Hardhat contract
to compare the Keccak-256 opcode path, the SHA-256 precompile path, and a
FIPS-vector-gated pure-Solidity SHA-512 reference. It evaluates deterministic
32-byte and 1,024-byte inputs, with three excluded warm-ups and 30 retained
\texttt{eth\_call} observations per algorithm/input cell. Algorithm order is
cyclically balanced. The measured quantity is the \texttt{gasleft()} delta
around the primitive path under Solidity 0.8.20, optimizer 200,
\texttt{viaIR=true}, and the Paris EVM target. This local instrument is not the
deployable SHA-512 path and cannot support a consensus, latency, finality, fee,
or public-testnet claim.
